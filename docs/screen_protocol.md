> 来源仓库：GitHub 私有仓库 `matianheng/JT_ZG_10-2`（骏通 10 寸安卓屏原厂 App，包名 `com.hndl.ui`，versionName 1.1.67）。

> 重要纠正：串口帧的组帧/解帧不在 MainActivity，而在 `MyUtils`（组帧/校验）与 `base/BaseActivity.java`（拆包分发）；MainActivity 只是继承 BaseActivity 并覆写各 CAN 帧回调。BaseActivity 中多数回调方法名带旧后缀（如 `getCanData_294`），比实际 CAN ID 小 4，系早期 nodeID=0x04 遗留，现 nodeID=0x08（`AppData.nodeID`），下文一律以 switch 中实际 ID 为准。

## 0. 链路总览

```
安卓 App (com.hndl.ui)
  │  串口 /dev/ttyHSL2，921600 baud（AppData.baudRate 初值 115200，打开时被覆写）
  │  经 JNI 本地库 "can"（SerialPort 模块 SeriaPortUtils.kt：startUartTaskJNI / sendUartFunJNI）
  ▼
屏内下位单片机（MCU，CAN 串口网关）
  │  两路 CAN（索引 0 / 1），波特率默认 250 kbps，可配 {100,125,250,500,666,1000}
  ▼
控制器（CANopen 风格节点，nodeID = 0x08）
```

- App 不直连 CAN 物理层；所有 CAN 收发都被封装成 ASCII 串口帧经 MCU 转发（出处：`CanSerialManager.java`、`MyUtils.constructSerialData/constructCanData`、`base/BaseActivity.parseSerialData/parseCanData`）。
- 发送门控：`CanSerialManager.sendBytes()` 仅当 `AppData.isCanData == true` 才真正发送。开机流程（`SplashActivity`）先置 false，收到 MCU 的 0x31 通知或延时 200ms 后置 true 并进入 ConfirmActivity；接收侧对 0x36 帧的解析同样受此标志门控（出处：`CanSerialManager.java`、`SplashActivity.java`、`BaseActivity.parseSerialData`）。
- MCU 另有一套 JNI 直通 API（`SeriaPortUtils.kt`）：`openCanPort/closeCanPort(canIndex, 波特率kbps)`、`setCanFilter`（16/32 位掩码列表）、`sendCanData(canIndex, canId, frameType 0=标准/1=扩展, len, data)`、`configCanRs`、心跳 `sendHeartBeat(0..15)`、工作模式 `setWorkModeFunJNI(0=透传/1=解析)`、`enterLowPower`、版本查询等。当前 App 代码实际只用到：串口收发 + `openCanPort/closeCanPort` 改波特率；其余接口未见调用点（出处：`SeriaPortUtils.kt`、`CanSerialManager.java`）。

## 1. 串口帧格式

出处：`utils/MyUtils.java` 的 `constructSerialData / constructSerialFilter / calcCRC`；`base/BaseActivity.parseSerialData`。

| 偏移 | 内容 | 说明 |
|---|---|---|
| [0] | `0x02` | 帧头（STX，二进制字节） |
| [1] | 命令字 | 二进制字节，见第 2 节 |
| [2] | 数据区长度 **低半字节** 的 ASCII 十六进制字符 | `intToHexChar`：0-9→'0'-'9'，10-15→'A'-'F'。注意低半字节在前，与常规相反 |
| [3] | 数据区长度 **高半字节** 的 ASCII 十六进制字符 | 同上 |
| [4 .. 4+len-1] | 数据区 | 长度字段即此区字节数（单字节长度，两字符最大表示 0xFF） |
| [4+len]（=总长-3） | `0x03` | 帧尾（ETX） |
| [总长-2] | 校验 **低半字节** ASCII 字符 | 低半字节在前 |
| [总长-1] | 校验 **次低半字节** ASCII 字符 | 校验值只用低 8 位 |

总长 = 数据区长 + 7。

**校验（名不副实，必须注意）**：`MyUtils.calcCRC` 实际是 8 位字节累加和，不是 CRC：对下标 1 .. 总长-4（即命令字 + 长度两字符 + 全部数据区，**不含**帧头/帧尾）逐字节求和（Java 有符号 byte 直接相加；当前数据区均为 ASCII <0x80，无负数问题），取低 8 位，再拆成两个十六进制字符（低半字节在前）发出。
`utils/CRC16Utils.java` 里确有 CCITT（多项式 0x1021 / 反转 0x8408）、Modbus（0x8005 / 0xA001）等真 CRC16 实现，但在已读源码中**没有任何调用点**，与本协议无关，不要被文件名误导。

**接收端不验校验**：`BaseActivity.parseSerialData` 只检查 `[0]==0x02` 且 `[总长-3]==0x03`，校验比对代码整段被注释。JNI 回调（`SerialPortUtils.recvMsg` ← `CanSerialManager.openSerialPort` 注册）把字节块整包交给 `handleSerialData`，解析函数默认整包即一帧；JNI/native 层如何按帧头帧尾切分字节流，在 Kotlin/Java 层不可见，**待定**。`CanSerialManager.iniSerialPortManager` 中有一套旧的 0x02/0x03 拼帧代码，整段被注释，未启用。

## 3. CAN 转发格式（串口数据区内的 CAN 包编码）

出处：`MyUtils.constructCanData`、`BaseActivity.parseCanData`。

数据区固定 **26 个 ASCII 字符**，承载一帧 8 字节 CAN 数据：

| 字符下标 | 内容 |
|---|---|
| [0] | CAN 通道号的单个十六进制字符。发送侧取静态变量 `MyUtils.canIndex`，默认 **1** 且 App 代码中从未改写 → App 发出的 CAN 帧一律走通道 1。接收侧解析出通道号但分发时不区分（仅打日志） |
| [1] | 数据长度字符（'8'） |
| [2..9] | CAN ID 的 8 个半字节字符，**低半字节在前**（`longToHex` 逐半字节输出）。ID 最高位 bit31 为帧类型标志：代码注释 0=标准帧、1=扩展帧；解析时 ID 取 `& 0x7FFFFFFF` |
| [10..25] | 8 个数据字节，每字节 2 个字符，同样低半字节在前 |

解析怪癖：`parseCanData` 长度 ≠ 26 直接丢弃；另外算了一个 `resultCode` = 数据区最后一字符（即数据字节 7 的高半字节），并无实际用途。

**波特率管理**（出处：`CanSerialManager.java`）：两路 CAN 索引 0/1，波特率分别存 MMKV 键 `can1Baud` / `can2Baud`，缺省 250（kbps）；合法集 {100, 125, 250, 500, 666, 1000}，其余值归 250。重配流程：`closeCanPort` → 等 80ms → `openCanPort`，最多重试 3 次，成功后回存 MMKV。

**App 主动发出的非 SDO CAN 帧**（均经 0x35 封装）：

| CAN ID | 周期/时机 | 数据 | 含义 |
|---|---|---|---|
| 0x01 | MainActivity onCreate、总线故障时、0x708 处理中 | {01,0,0,0,0,0,0,0} | **推测**为 CANopen NMT 启动类帧，未证实 |
| 0x718（=0x710+nodeID） | MainActivity 约每 100ms | {01,0,…} | 与 0x708 构成心跳看门狗（发送时 `reckonByTime` 自增）；目标节点/语义**待定**（也可解读为发往节点 0x18） |
| 0x228（=0x220+nodeID） | 每 500ms | 字节0=公历年低字节、1=月、2=日、3=星期（周一=1…周六=6、周日=0）、4=时、5=分、6=秒、7=0 | 时钟同步帧 |
| 0x608（=0x600+nodeID） | 各功能页按需 | SDO 风格参数帧，见第 5 节 | 参数读写通道 |

## 5. 参数通道（SDO 风格对象字典）

出处：各功能页 Activity。App 经串口命令 0x35 发 CAN 帧至 **0x608**（0x600+nodeID），控制器以 **0x588**（0x580+nodeID）应答。帧数据 8 字节布局：

| 字节 | 内容 |
|---|---|
| [0] | 命令说明符：读请求 0x43（另见 0x4F=读 1 字节对象、0x4B=读 2 字节对象，厂商用法不统一）；写 4/2/1 字节分别为 0x23 / 0x2B / 0x2F；应答统一以 0x60 开头；0x80 开头被 App 当作该对象的失败/中止应答（如 0x2010、0x2025 的处理） |
| [1] | 对象索引低字节 |
| [2] | 对象索引高字节 |
| [3] | 子索引 |
| [4..7] | 值，小端 |

通用收尾：多数修改流程在写成功后写对象 **0x1010:01 = ASCII "save"**（73 61 76 65，即 CANopen 标准存参签名）保存参数；设置类页面的典型交互是同一帧每 100ms 重发直到收到对应 0x60 应答。

### 5.1 系统对象

| 对象 | 读/写 | 数据 | 含义 | 出处 |
|---|---|---|---|---|
| 0x1010:01 | 写 | "save" | 保存参数到非易失存储 | 几乎所有设置页 |
| 0x1011:01 | 写 | "load"（6C 6F 61 64） | 载入/恢复参数；车型切换后发送 | ModelSelectionActivity |
| 0x1015:01/02/03 | 写 0x2F | 字节4：0x01 / 0x02 | 参数组恢复/复位命令：子索引 01=空钩参数组、02=砝码 1 组、03=砝码 2 组；值 0x01=恢复最近一次参数，0x02=参数复位 | EmptyHookDebuggingActivity（:01）、WeightActivity（:02/:03） |
| 0x1017:01 | 写 0x2F | 字节4：0x00 或 0x01 | 臂节切换流程中与 0x2028 同发（五节臂时 0x01、六节臂时 0x00，与 0x2028 取值恰好相反）；CANopen 中 0x1017 本为心跳生产者时间，此处用法不标准，确切语义**待定** | ArmStateSelectionActivity |

## 7. CAN 0x1F8 帧 DI/DO 位定义

出处：`InputOutputStatusActivity.getCanData_1F4`（方法名仍带旧后缀）。位序按该页列表顺序抄录；IO 控制器口径（dataSrc=1）与 40 点控制器口径（dataSrc=2）不同，下表以基础（IO）集为主，40 点扩展单列。

**DO（字节0，bit0→bit7）**：主控阀、油缸切换阀、起幅/缩臂阀（原文 lifting_shrinking_arm_valve）、落幅/伸臂阀、过卷保护阀、过放保护阀、蜂鸣器、油冷器/空调控制。
**dataSrc=2 扩展 DO**：字节1 bit0-7 = 前雨刮高速、前雨刮低速、顶雨刮低速、前洗涤、顶洗涤、转台工作灯、吊臂工作灯、示廓灯；字节2 bit0-6 = 三色灯绿、三色灯黄、三色灯红、空调控制端、发动机熄火控制、推杆伸、推杆缩；车型 26/27/29 时字节3 bit3 = 微动阀。
**车型 32/36 替代映射**：字节2 bit7 + 字节3 bit0-3 依次 = 配重/空调切换阀、配重前移阀、配重后移阀、配重主控阀、微动阀。

**DI（字节4，bit0→bit7）**：bit0 主令开关、bit1 强制开关、bit2 超载解除（钥匙）、bit3 油缸切换开关、bit4 变幅/伸缩切换开关、bit5 120°判断、bit6 过卷信号、bit7 取力信号；另字节6 bit6 → 过放信号（代码中 input[7] 取自字节6 bit6，与下条 40 点扩展对字节6 的用法重叠，属原厂代码复用，照实记录）。
**dataSrc=2 扩展 DI**：字节5 bit0-7 = 副钩过卷信号、前雨刮复位、顶雨刮复位、油冷器开关、空调开关、前雨刮低速开关、前雨刮高速开关、顶雨刮低速开关；字节6 bit0-7 = 前雨刮洗涤开关、顶雨刮洗涤开关、转台工作灯开关、吊臂工作灯开关、示廓灯开关、分流阀（开关量）、主卷过放、副卷过放（解除）；字节7 bit0-3 = 接近开关、推杆伸到位、推杆缩到位、欠压信号。
**车型 32/36 替代 DI**：字节7 bit4/bit5 = 配重前移开关、配重后移开关。

> 注：同一帧字节7 在 MainActivity 中被解释为 bit2=五节臂模式、bit1=六节臂模式（见第 6 节），与 IO 页对字节7 bit0-3 的解释并存。两种解释分别出现在不同页面/口径下，究竟是模式复用还是原厂笔误，**待定**，自研侧引用时须实测确认。

## 10. 自研对接注意事项（源码事实推论）

- 这套协议本质是「ASCII 串口帧裹 CAN 帧 + CANopen SDO 风格参数字典」，控制器节点 0x08、SDO 通道 0x608/0x588 与 CANopen 习惯一致（0x1010 存参签名 "save"、0x1011 恢复签名 "load" 均为标准值），自研固件按此实现即可与原屏 App 互通。
- 串口校验只是 8 位累加和且接收端根本不验，链路可靠性靠帧头/帧尾+长度形态；自研侧若沿用，接管后建议至少在 MCU 侧补验，但改协议前须确认原屏兼容性。
- 力限核心量（吊重/额定/力矩%、幅度、高度、L1、臂长、角度、P1、P2、过卷位、DI/DO）全部走周期帧明文小端定点数，台架复现与抓包对账成本低。
- 安全相关量（过卷 bit、超载 bit、传感器故障编码）在 0x2D8 一帧内齐备；超载记录的触发条件（力矩%>100 且 0x2D8 字节1、2 为 0）说明原厂把「传感器故障时不记超载」写进了屏侧逻辑，控制器侧同类联锁需另行实测确认。

## 11. 厂家协议手册对案附记（2026-11-11，《DL-IO1210/1824/4032 CANBUS 通信协议 V1.3.0》）

用户提供厂家正式手册，与本文（屏源码恢复）、channel_labels_v1.md（固件追踪）三方互证，关闭以下悬案：

- **压力工程单位定案**：0x1B0+nodeID 帧压力分辨率 0.01 **MPa**（第 9 节原标“单位待定”关闭）；长度分辨率 1cm、角度 0.01° 均与手册一致。
- **0x298 字节 6-7 定案**：实际重量（**修正前**，调重用）；字节 0-1 额定、2-3 实际（修正后，显示）、4-5 百分比——与固件侧载荷结构体四 double 顺序严丝合缝。
- **0x1E8 定案**：重量调试数据帧（L1/DW/A1/KW），由 SDO 0x1012 请求后周期发送。
- **0x2D8 故障帧**与手册第 9 节逐位一致（传感器故障 2 位编码：1=信号中断、2=AD 高于上限，与固件有效性判定状态 1/2 对应）。
- **0x1017 定案**：推杆伸/缩命令（子索引 1/2，ctrl 0=伸、1=缩）；臂节模式是 **0x2028**（0=五节臂、1=六节臂）——第 5 节原“0x1017 语义待定”关闭。
- **车型 ID 表**（0x2022）：0x17=JTC10H5、0x18=JTC10H6、0x20=JTC12H6B-I、0x22=JTC12H6B；主机厂 ID 默认 0x01=骏通。
- **NMT 状态机（自研必须复刻）**：节点上电发一次状态 0x00 后停在**预操作状态**（心跳与 SDO 开、**PDO 关闭不上传数据**），须收到上位机 **启动命令**才进操作状态开始上传；上位机以 0x710+nodeID 周期发心跳（1000ms），下位机 0x700+nodeID 回（Byte2 hw_id：0x03=DL-IO1824）；**连续 8 秒收不到主机心跳判通信故障**（心跳 Byte1 com_status 置 0）。
- 手册**通篇无固件升级/Bootloader 章节**——专用刷写工具的升级机制不在此文档内。
- SDO 对象与本文第 5 节互证一致：0x2010 工况、0x2011 结构参数（中心距/底盘高，0.01m）、0x2012 幅度修正（-20~100 有符号）、0x2013/0x2014 零点/满点（子索引 01=L1/02=L2/03=A1/04=A2/05=P1/06=P2）、0x2016/0x2017 一键调零/调满、0x2018 P1/P2 修正系数（80~120，与固件内 k∈[80,121] 吻合）、0x2019 砝码值、0x2020 调重参数开关、0x2021 范围限制、0x2023 版本号、0x2025~0x2027 虚拟墙、0x2030 协议版本号；存参 0x1010 写 "save"、恢复 0x1011 写 "load"。
- 端口模式可配置（SDO 0x2100/0x2101）：X 口 0x08=AI 电压/0x09=AI 电流/0x0A=AI 电阻/0x0B=DI（默认）/0x0C、0x0D=PWMI（仅 X00~X03）；Y 口 0x01=DO/0x02=PWM 占空比。RPDO：0x200+nodeID 设 PWM 占空比、0x220+nodeID 实时时钟（500ms）。
